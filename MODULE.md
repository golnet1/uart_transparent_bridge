# Pass-Through UART — описание работы модуля

Документ описывает внутреннее устройство прошивки **Pass-Through UART v1.0.4**:
как устроены подсистемы, в каком порядке они запускаются, как данные идут между
UART, вебом, Telnet, MQTT и журналом. Для пользовательских инструкций см.
[README.md](README.md).

---

## 1. Назначение

ESP32 работает прозрачным мостом между двумя последовательными портами:

```
внешнее устройство --UART1--> ESP32 --UART2--> внешнее устройство
внешнее устройство --UART2--> ESP32 --UART1--> внешнее устройство
```

Весь проходящий трафик может дублироваться в USB-UART (UART0) в виде
плотного `HEX | ASCII` (например `41540D |"AT\r"|`, без пробелов между байтами).
Управление и отправка команд доступны из четырёх мест:

- веб-интерфейс (встроенный HTML + WebSocket);
- Telnet (порт 23);
- USB-терминал (UART0, 115200);
- HEX-каналы: адресная строка браузера и MQTT.

Дополнительно: автокоманда от самого ESP32, NTP-часы, OTA, сканирование Wi-Fi.

## 3. Аппаратная часть и пины

| Канал | Порт | TX | RX | Скорость | Назначение |
|-------|------|----|----|----------|------------|
| UART1 | `UART_NUM_1` | GPIO4 | GPIO5 | 115200 по умолчанию (изменяемая) | Подключённое устройство №1 |
| UART2 | `UART_NUM_2` | GPIO25 | GPIO26 | 9600 по умолчанию (изменяемая) | Подключённое устройство №2 |
| USB | `UART_NUM_0` | GPIO1 | GPIO3 | 115200, фиксированная | Зеркало трафика + консоль команд |

Пины заданы макросами `UART1_TX_PIN`, `UART1_RX_PIN`, `UART2_TX_PIN`,
`UART2_RX_PIN`, `USB_TX_PIN`, `USB_RX_PIN` в `main/uart_bridge.c`.

Все порты настраиваются как **8N1** без аппаратного контроля потока:
`uart_param_config()` → `uart_set_pin()` → `uart_driver_install()`
(RX-буфер 512, TX-буфер 256, очередь событий 16).

Системная консоль ESP-IDF отключена (`CONFIG_ESP_CONSOLE_NONE=y`), поэтому UART0
полностью доступен нашему драйверу. Все логи `ESP_LOGx` перехватываются функцией
`app_log_vprintf()` и уходят в шину событий как `EV_SYS`.

## 4. Запуск (`app_main()`, `main/main.c`)

Порядок важен: шина событий и конфигурация должны существовать до того, как
любой модуль начнёт публиковать события или логи.

1. `nvs_flash_init()` — при ошибке `NO_FREE_PAGES` / `NEW_VERSION_FOUND` память
   стирается и инициализируется заново.
2. `event_bus_init()` — создаётся мьютекс журнала.
3. `config_load()` — читается blob `uart_moyka/cfg`; при отсутствии берутся
   значения по умолчанию.
4. `charset_init()` — читается настройка кодировки (`uart_moyka/charset`).
5. `auth_init()` — читается/создаётся хеш пароля (`uart_moyka/auth` + `authver`).
6. `esp_log_set_vprintf(app_log_vprintf)` — логи ESP-IDF перенаправляются в шину.
7. `ESP_LOGI("запуск ...")`.
8. `uart_bridge_init()` — драйверы UART и задачи приёма.
9. `cli_init_usb()` — сессия USB-терминала, приветствие и приглашение `>`.
10. `wifi_init()` — AP + STA, обработчики событий.
11. `time_sync_init()` — запуск SNTP.
12. `web_init()` — HTTP-сервер и WebSocket.
13. `telnet_init()` — Telnet-сервер.
14. `ota_init()` — подтверждение OTA-слота (отмена rollback).
15. `mqtt_init()` — MQTT-клиент, если задан режим и URI.
16. Баннер с IP, скоростями и подсказкой печатается в USB; событие «готов к работе»
    уходит в журнал.

Итог: к моменту появления первых сетевых подключений все подписчики шины уже
созданы.

## 5. Конфигурация (`config.c`)

Вся сохраняемая конфигурация — один blob `cfg` в пространстве имён `uart_moyka`
(NVS). Отдельно хранятся `auth` (хеш пароля), `authver` и `charset`.

### 5.1 Значения по умолчанию

| Поле | Значение | Смысл |
|------|----------|-------|
| `baud1` | 115200 | скорость UART1 |
| `baud2` | 9600 | скорость UART2 |
| `auto_baud1` | `false` | автоопределение скорости UART1 |
| `auto_baud2` | `false` | автоопределение скорости UART2 |
| `baud_probe` | `AT\|AT+GMR` | команды опроса (через `\|`), ждём ответ `OK`/`ERROR` |
| `bridge` | `true` | сквозная пересылка включена |
| `echo` | `false` | дублирование в источник выключено |
| `mirror` | `true` | зеркало трафика в USB включено |
| `syslog` | `false` | системные логи в USB выключены |
| `usb_target` | `3` | команды USB/telnet идут на оба UART |
| `auto_ms` | `0` | автокоманда выключена |
| `auto_target` / `auto_text` | `1` / `AT` | параметры автокоманды |
| `wifi_ssid` / `wifi_pass` | пусто | STA не подключён, работает только AP |
| `ota_url` | пусто | URL прошивки не задан |
| `cmd_mode` | `0` | HEX-канал: адресная строка |
| `cmd_target` | `3` | цель HEX-команд по умолчанию — оба UART |
| `mqtt_uri` | пусто | брокер не задан |
| `mqtt_topic` | `pass-through-uart` | базовый топик |
| `ntp_server` | `pool.ntp.org` | сервер времени |
| `ntp_tz` | `MSK-3` | часовой пояс (UTC+3) |

### 5.2 Миграция при обновлении прошивки

Новые поля добавляются **в конец** структуры `app_config_t`. При загрузке:

```c
size_t len = sizeof(s_cfg);
nvs_get_blob(h, "cfg", &s_cfg, &len);   // len может быть меньше,sizeof(сейчас)
```

Сначала структура заполняется `defaults()`, затем поверх копируется столько
байт, сколько реально сохранено. Остальные поля остаются значениями по
умолчанию. Это сохраняет SSID/пароль Wi-Fi и остальные настройки после прошивки
новой версии с расширенной конфигурацией.

Дополнительно проверяются диапазоны (`baud1/baud2` 1200…3000000,
`usb_target` 1…3, `cmd_mode` 0…2, `cmd_target` 1…3) и завершаются `\0` все
строковые поля — защита от мусора в NVS.

`config_mut()` возвращает указатель на структуру; после изменений вызывающий
обязан вызвать `config_save()`, который делает `nvs_set_blob()` + `nvs_commit()`.

## 6. Шина событий и журнал (`event_bus.c`)

### 6.1 Типы событий (`app.h`)

| Тип | Значение | Метка в журнале |
|-----|----------|-----------------|
| `EV_FROM1` | принято с UART1, передано на UART2 | `UART1 > UART2` |
| `EV_FROM2` | принято с UART2, передано на UART1 | `UART2 > UART1` |
| `EV_FROMUSB` | команда из USB-терминала | `USB > UART` |
| `EV_TO1` | локальная отправка в UART1 | `LOCAL > UART1` |
| `EV_TO2` | локальная отправка в UART2 | `LOCAL > UART2` |
| `EV_SYS` | системные сообщения / логи ESP-IDF | `SYS` |
| `EV_OTA` | события обновления | `OTA` |
| `EV_WIFI` | события Wi-Fi | `WIFI` |

Маски: `SUB_ALL` (всё), `SUB_TRAFFIC` (обмен данными), `SUB_SYS` (системные).

### 6.2 Формат строки журнала

- **До NTP-синхронизации:** `[ЧЧ:ММ:СС.ммм] [МЕТКА] ...` — время с момента загрузки.
- **После синхронизации:** `[дд.мм ЧЧ:ММ:СС] [МЕТКА] ...` — реальное локальное время.

Трафик выводится как `41 54 0D ... |"AT\r"|` (до 96 байт, дальше `...`),
строковые сообщения — как обычный текст.

### 6.3 Кольцевой буфер и подписчики

- Ёмкость журнала — **32 КБ** в RAM; при переполнении вытесняются самые старые
  байты. Журнал сбрасывается при перезагрузке.
- Каждая запись хранится как строка + один `'\n'`; завершающие `\r`/`\n` из
  ESP-IDF-логов срезаются в `format_message()`, иначе счётчик и `/api/log`
  считали бы пустые строки за отдельные сообщения.
- `event_bus_log_lines()` считает реальные записи в буфере. `/api/log?n=N`
  возвращает **последние N** (ищет `(N+1)`-й перевод строки с конца); веб
  грузит стартовую порцию `n=300` и держит в DOM не более 600 строк. Поэтому при
  длинном журнале бейдж «строк в буфере» может быть больше видимого списка —
  это нормально.
- Максимум **10 подписчиков**. Подписка — `event_bus_subscribe(queue, mask)`,
  отписка — `event_bus_unsubscribe(queue)`.
- Публикация (`event_bus_publish` / `event_bus_publish_str`) под мьютексом
  форматирует строку, добавляет в кольцо и рассылает указатели `app_msg_t*` по
  очередям подписчиков. **Память освобождает подписчик** (`free(msg)`).
- Защита от рекурсии: `uart_write_bytes()` при ошибке пишет в `ESP_LOG`, который
  снова вызывает публикацию. Флаг `s_publishing` под critical section прерывает
  повторный вход.
- Опция `syslog` включает дублирование `EV_SYS` в USB (только после того, как
  драйвер UART0 установлен).

Подписчики шины:

| Подписчик | Маска | Что делает |
|-----------|-------|------------|
| `web.c` / `ws_events_task` | `SUB_ALL` | рассылает JSON `{type,ts,line}` через WebSocket |
| `mqtt_client.c` / `traffic_task` | `SUB_TRAFFIC` | публикует `line` в `<topic>/traffic` |
| `telnet.c` (каждый клиент) | `SUB_TRAFFIC \| SUB_SYS` | выводит строки в терминал, если `monitor on` |

## 7. UART-мост (`uart_bridge.c`)

### 7.1 Задачи

| Задача | Стек | Приоритет | Описание |
|--------|------|-----------|----------|
| `uart1_rx` | 6144 | 12 | читает UART1 блоками по 128 байт, таймаут 20 мс |
| `uart2_rx` | 6144 | 12 | читает UART2, та же логика |
| `usb_rx` | 10240 | 12 | читает UART0, собирает строки команд для CLI |
| `auto_cmd` | 4096 | 5 | периодическая автокоманда |

Большой стек `usb_rx` нужен из-за глубокой цепочки `CLI → event_bus → format_message`.

### 7.2 Маршрутизация

При приёме байтов с UART1 (`uart_rx_task`, `ch == 1`):

1. `s_rx1 += n`.
2. `forward(EV_FROM1, PORT2, "UART1", buf, n)`:
   - если `bridge == true` — `uart_write_bytes(PORT2, ...)`;
   - `s_tx2 += n` (счётчик пополняется независимо от флага `bridge`);
   - `event_bus_publish(EV_FROM1, ...)`;
   - если `mirror == true` — `mirror_to_usb("UART1", ...)`.
3. Если `echo == true` — принятые байты возвращаются обратно в UART1.

Для UART2 всё симметрично (`EV_FROM2`, приём на UART1, `echo` в UART2).
Таким образом мост **двунаправленный**: `UART1 ⇄ UART2`.

Приём с USB (`ch == 0`) не пересылается напрямую в UART: публикуется `EV_FROMUSB`
и байты отдаются в `cli_usb_bytes()`, который собирает строку до `\n` и вызывает
`cli_process()`.

### 7.3 Отправка команд

`uart_bridge_send(target, data, len)`:

| `target` | Куда пишет |
|----------|------------|
| `0` | только USB (UART0) |
| `1` | UART1 |
| `2` | UART2 |
| `3` | оба UART |

Для UART-направлений обновляются счётчики `s_tx1/s_tx2`, публикуются события
`EV_TO1/EV_TO2` и (при `mirror`) печатается строка `LOCAL > UARTn` в USB.
Отправку инициируют: веб `/api/send`, URL `?hex=`, MQTT, CLI `send/sendhex/raw`,
автокоманда.

`uart_bridge_apply_config()` применяет новые скорости без перезапуска (driver
`uart_set_baudrate` для UART1/2). Если включено автоопределение, смена скорости,
команд опроса или самого выключателя вызывает повторный опрос.

### 7.4 Автокоманда

Задача `auto_cmd` каждые `auto_ms` миллисекунд отправляет строку `auto_text` + `\r\n`
на цель `auto_target` (`1`, `2`, `both`/`3`, `usb`/`0`). При `auto_ms <= 0`,
пустом тексте или цели `0` задача спит по 250 мс.

### 7.5 Автоопределение скорости (`auto_baud1/2`, `baud_probe`)

Для каждого UART есть свой выключатель. Опрос выполняется прямо в задаче
`uart1_rx` / `uart2_rx`: когда `uart_bridge_apply_config()` выставляет
`s_detect_pending[ch]` (включение, смена `baud1/baud2` или `baud_probe`), задача
вызывает `detect_baud(port, ch)`.

Алгоритм:

1. `split_probes()` разбивает строку `baud_probe` разделителями `|`, `;`, `,`,
   пробел; по умолчанию `AT|AT+GMR`.
2. Перебираются скорости 1200…921600 бод. Для каждой скорости буфер ввода
   сбрасывается (`uart_flush_input`), затем отправляются все команды опроса с
   `\r\n`.
3. `has_reply()` ищет в ответе `ok` или `error` без учёта регистра. Первый
   совпавший baud фиксируется в `s_detected_baud[ch]`, цикл прерывается.
4. На время опроса `s_detect_active[ch] = true`; обе RX-задачи приостанавливают
   сквозную пересылку, чтобы пробовые команды и ответы не попали в другой UART.
5. Если ответа нет — в лог пишется `ESP_LOGW`, порт остаётся на скорости из
   конфигурации, `s_detected_baud[ch] = 0`.

Результат доступен через `uart_bridge_detected_baud(1|2)` (используется в
`/api/status` и CLI `status`). Настройки сохраняются в NVS; новые поля добавлены
в конец `app_config_t`, поэтому старый blob конфигурации корректно дополняется
значениями по умолчанию.

## 8. CLI: USB-терминал и Telnet (`cli.c`, `telnet.c`)

### 8.1 Сессии и «цель по умолчанию»

`cli_session_t` содержит:

- `target` — цель по умолчанию, берётся из `config_get()->usb_target` при
  `cli_session_init()`. Значения `1`/`2`/`3` (оба); `0` («USB») используется
  редко и означает локальный ввод.
- `raw` — режим «весь ввод сразу в UART» без разбора команд.
- `out` — функция вывода (`usb_out()` для USB, `telnet_out()` для Telnet).

**«Цель по умолчанию (USB/telnet)»** в вебе — это именно `usb_target`. Она задаёт
стартовую цель для новых сессий. Команда `target 1|2|both` меняет цель только
текущей сессии и не сохраняется. `send 1 AT` / `sendhex 2 41 54 0D` задают цель
для одной отправки. В USB-терминале локальные команды можно писать с префиксом
`/` (`/help`, `/status`), чтобы отличать их от текста для UART.

### 8.2 Набор команд

```
help / ?                          список команд
status                            состояние, счётчики, IP
target 1|2|both|usb               цель текущей сессии
raw on|off                        весь ввод сразу в UART
send <1|2|both> <текст>           отправить текст
sendhex <1|2|both> <AA BB CC>     отправить байты (1 или 2 цифры на байт)
baud1 <bps> / baud2 <bps>         скорость UART
autobaud 1|2|both|off [команды]   автоопределение по ответу OK/ERROR
bridge|echo|mirror|syslog on|off  режимы моста
log [N] / log clear               журнал
wifi <ssid> <password>            подключиться к AP
ota <http://.../fw.bin>           обновление по воздуху
auto <мс> <1|2|both|usb> <текст>  автокоманда (0 = выкл)
charset cp866|utf8                кодировка вывода терминала
passwd <новый>                    смена пароля (веб + telnet)
cmdmode url|mqtt|both             канал HEX-команд
mqtt <uri> <topic> [user] [pass]  брокер MQTT
time                              текущее время (NTP)
ntp <server> [tz]                 сервер NTP и часовой пояс
monitor on|off                    только Telnet: показывать трафик
reboot                            перезагрузка
```

### 8.3 Telnet

- Порт **23**, до **4** клиентов, один task `telnet` на `select()`.
- При подключении: negotiations `IAC WILL ECHO`, `IAC WILL SGA`, затем запрос
  `Password: `. Ввод пароля идёт **без echo**, таймаут **60 с**. При неверном
  пароле соединение закрывается. IAC-последовательности обрабатываются
  конечным автоматом (включая подпереговоры `SB/SE`), ответы всегда по 3 байта.
- После успешной авторизации клиент подписывается на `SUB_TRAFFIC | SUB_SYS`;
  `monitor off` снимает подписку. Строки проходят через `charset_convert()`.
- Команда `monitor` обрабатывается локально в `telnet.c`, остальные — в `cli.c`.

## 9. Кодировка (`charset.c`)

Внутри прошивки все строки — UTF-8. По умолчанию вывод в терминалы переводится
в **CP866** (`s_cp866 = 1`), иначе Windows-терминал показывает «кракозябры».
Настройка хранится в NVS и меняется командой `charset cp866|utf8`.

`charset_convert()` — безопасно декодирует 1…4-байтные последовательности
UTF-8 и подставляет `?` для неподдерживаемых символов; при `utf8` просто
возвращает копию строки. Вызывающий обязан `free()`.

## 10. Аутентификация (`auth.c`)

- Пароль **одновременно является путём** в URL. По умолчанию — `sec`.
- Хранится только хеш **SHA-256** в NVS: `uart_moyka/auth` (32 байта) +
  `uart_moyka/authver = 1`. Открытым текстом пароль не сохраняется. `authver`
  защищает от несовместимого старого хеша после обновления прошивки.
- Ограничения на пароль: латиница, цифры и `. _ - ~`, длина 1…32.
- Токен для cookie **детерминированный**: первые 16 байт хеша в HEX
  (например, `add93534eeb463800fe0ed0946048d33`). При смене пароля токен
  меняется автоматически; отдельного хранилища сессий нет.
- Один и тот же пароль используется для веба и Telnet. Сменить можно:
  - в вебе (карточка «Безопасность»: текущий, новый, **повтор нового** —
    сервер получает запрос только после совпадения полей в браузере);
  - командой `passwd <новый>` в CLI.

Точные сообщения веб-авторизации:

| Ситуация | Ответ |
|----------|-------|
| `GET /` | `401 Password is not specified` |
| неверный путь | `401 Wrong password` |
| неверный `old` при смене | `{"ok":false,"msg":"Wrong password"}` |
| поля не заполнены | `{"ok":false,"msg":"Password is not specified"}` |
| new != repeat | `Passwords do not match` (проверка в JS) |

## 11. Веб-сервер (`web.c`, `web_ui.cpp`)

### 11.1 Общее

- `esp_http_server` на порту **80**, `max_open_sockets = 13` (3 зарезервированы
  HTTPD), до **8** WebSocket-клиентов. `CONFIG_LWIP_MAX_SOCKETS=16`.
- Веб-страница — один встроенный в прошивку HTML (`main/web_ui.cpp`, ~25 КБ),
  без SPIFFS и внешних CDN. Интерфейс адаптивный, тёмная тема.
- Язык интерфейса выбирается выпадающим списком с картинками флагов `RU` / `EN`
  в шапке (встроенные SVG data URI, без внешних CDN; скрытый `<select id="lang">`
  служит для состояния и события `change`).
  Выбор хранится в `localStorage['ptuart.lang']` (по умолчанию `ru`). Функции
  `applyLang()`, `t(key[, vars])`, `trMsg()` и `trOta()` в `web_ui.cpp` переводят
  статические подписи (`data-i18n`, `data-i18n-html`, `data-i18n-ph`,
  `data-i18n-title`) и динамические строки; ответы сервера — по префиксу `msg:`.
  Uptime и OTA-статус форматируются на клиенте, чтобы не показывать русский текст
  в английском режиме. Строки журнала прошивка пишет по-русски; `trLog()` переводит
  их по словарю `LOG_DICT`, а оригиналы хранятся в `LOG_RAW` — при смене языка
  `rerenderLog()` переводит заново и уже показанные строки. IP, числа и топики
  в строках не затрагиваются.
- Секретный путь ловится последним обработчиком `/*` (wildcard). `req->uri`
  содержит и query-строку, поэтому пароль выделяется только до символа `?`.
- Успешный вход выставляет cookie `PTUART=<token>; Path=/; HttpOnly;
  SameSite=Lax; Max-Age=86400`. Все `/api/*` и `/ws` требуют валидную cookie.
  При `401` JS возвращает пользователя на секретный путь.

### 11.2 HTTP API

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/<пароль>` | HTML панели; с `?hex=`/`?log=` — HEX-канал (см. §12) |
| POST | `/api/passwd` | смена пароля: `{old,new}` |
| GET | `/api/status` | полное состояние устройства |
| POST | `/api/config` | сохранение настроек; побочные эффекты — см. ниже |
| POST | `/api/send` | `{target,format:"text"\|"hex",data}` → `uart_bridge_send()`; без `target` — оба UART |
| GET | `/api/log?n=200` | последние N строк журнала массивом `lines` |
| POST | `/api/log/clear` | очистка журнала |
| GET | `/api/wifi/scan` | результат блокирующего сканирования AP |
| POST | `/api/ota` | `{url}` — запуск обновления |
| POST | `/api/reboot` | перезагрузка через 500 мс |
| GET | `/ws` | WebSocket (только GET для handshake) |

`/api/send`: поле `data` обязательно, `format` — `text` (по умолчанию) или `hex`;
`target` принимает `0` (USB), `1`, `2`, `3` или строки `usb`, `uart1`, `uart2`,
`both`, `all`. Незаданный/некорректный `target` трактуется как `3` — отправка
на оба UART (`target_from_json(root, 3)`). Ответ содержит выбранную цель.

**`/api/status`** возвращает:

```
version, uptime, uptime_text, baud1, baud2, auto_baud1, auto_baud2, baud_probe,
baud1_detected, baud2_detected, bridge, echo, mirror, syslog,
usb_target, auto_ms, auto_target, auto_text, log_lines,
ota_url, ota_busy, ota_last, cmd_mode_name,
mqtt:  {mode,target,target_effective,uri,uri_effective,topic,user,connected},
time:  {synced,server,tz,str,epoch,offset},
counters: {rx1,rx2,tx1,tx2},
wifi:  {ap_ip,sta_ip,connected,ap_enabled,rssi,ssid}
```

`uptime` — секунды с boot, `uptime_text` — готовый формат для веба/CLI:
до 60 с «N с», до 60 мин «N мин SS с», до 24 ч «N ч MM мин»,
дальше «N д HH ч MM мин».

**`/api/config`** принимает те же поля конфигурации (и `ntp_server`, `ntp_tz`).
После `config_save()` выполняются только нужные действия:

- изменились `baud1/baud2`, `auto_baud1/2`, `baud_probe` → `uart_bridge_apply_config()`;
- изменились `wifi_ssid/wifi_pass` → `wifi_reconnect()`;
- изменились `cmd_mode`/MQTT-поля → `mqtt_apply_config()`;
- изменились `ntp_server/ntp_tz` → `time_sync_apply()`.

Пустое поле `mqtt_pass` означает «оставить прежний пароль».

**Резервная копия настроек:**

```
GET  /api/config/export   → JSON с Content-Disposition: attachment
POST /api/config/import   → применение файла
```

Разбор JSON вынесен в `config_apply_json(cfg, root, import_mode, &flags)` —
одинаково используется веб-формой и импортом. Отличие импорта: пустой
`mqtt_pass` очищает сохранённый пароль, а поле `auth_hash` (64 HEX-символа)
восстанавливает хеш веб-пароля через `auth_restore_hash_hex()`. После этого
`auth_current_token()` подставляется в `Set-Cookie`, поэтому текущая сессия
остаётся авторизованной. Формат файла:

```json
{
  "format": "pass-through-uart-config",
  "config_format": 1,
  "app_version": "1.0.4",
  "saved_at": "20.11 03:30:00",
  "auth_hash": "...",
  "config": { /* все поля app_config_t */ }
}
```

Импорт принимает и «плоский» JSON без обёртки `config`. Поведение при
применении то же, что у `/api/config`: перезапускаются MQTT/Wi-Fi/NTP по
изменившимся полям, UART-скорости перепрошиваются при `baud_changed`.

### 11.3 WebSocket и живой монитор

`ws_events_task` подписан на `SUB_ALL`; каждое событие превращается в
`{"type":<номер>,"ts":<мс>,"line":"..."}` и рассылается через
`httpd_ws_send_frame_async()` всем активным клиентам. Клиентские текстовые
кадры игнорируются.

Интерфейс (`web_ui.cpp`) содержит карточки:

1. **Сквозной мост UART** — переключатели bridge/echo/mirror/syslog, скорости,
   выключатели автоскорости `autoBaud1/autoBaud2`, поле команд `baudProbe`,
   подсказку `baudHint` с результатом опроса, счётчики RX/TX и подсказку о пинах.
   Все элементы сохраняются сразу при изменении (`onchange` → `POST /api/config`
   → NVS); отдельной кнопки «Применить настройки» в этой карточке нет.
2. **Отправка команды** — выбор цели (1/2/оба/USB), формат (текст/HEX),
   поле ввода, быстрые кнопки AT, «Цель по умолчанию (USB/telnet)», автокоманда.
   Цель по умолчанию, интервал и текст автокоманды сохраняются сразу при
   изменении (`onchange` → `POST /api/config`).
3. **Каналы команд (HEX)** — режим (адрес/MQTT/оба), цель, настройки брокера,
   пример URL и топиков. Изменения сохраняются кнопкой «Применить каналы», но
   до нажатия автообновление их не затирает.
4. **Живой монитор** — статус WebSocket, **часы**, выпадающий фильтр
   «Все сообщения / Системные / Команды», кнопка «Очистить», автопрокрутка
   и счётчик строк; лог подгружается через `/api/log?n=300`. Фильтр работает
   и по уже загруженным, и по живым строкам: системными считаются теги
   `[SYS]`, `[OTA]`, `[WIFI]`, командами — `[UART1 > UART2]`, `[UART2 > UART1]`,
   `[USB > UART]`, `[LOCAL > UART1/2]`. Счётчик показывает общее число строк
   в буфере устройства, а не количество после фильтра.
5. **Wi-Fi** — состояние AP/STA, сканирование SSID с фильтром, подключение.
6. **Время (NTP)** — сервер и TZ, кнопка «Применить время».
7. **OTA** — URL прошивки, «Прошить», «Перезагрузить», а также кнопки
   «Сохранить настройки в файл» / «Восстановить из файла».
8. **Безопасность** — текущий/новый/повтор пароля.

Обновление статуса — раз в 2,5 с; при потере WebSocket — переподключение раз в 1,5 с.
Изменённые, но ещё не сохранённые поля помечаются как «грязные» и исключаются
из этого обновления; поэтому выпадающие списки в «Каналах команд» и «Отправке
команды» не прыгают. После успешной записи в NVS метка снимается.

**Часы в мониторе.** Сервер отдаёт `time.epoch` (секунды Unix) и `time.offset`
(минуты относительно UTC, вычисляются через `strftime("%z")`). Браузер хранит
`clockOffset = epoch*1000 - Date.now()` и раз в секунду показывает локальное
время `dd.mm HH:MM:SS`, используя `Date` в UTC + смещение TZ. После NTP бейдж
становится зелёным; до синхронизации — «Время: синхронизация…».

## 12. Каналы HEX-команд

Режим хранится в `cmd_mode`: `0` — URL, `1` — MQTT, `2` — оба. Выбор в вебе
(карточка «Каналы команд») или командой `cmdmode url|mqtt|both`. `cmd_target`
(`1`/`2`/`3`) — цель по умолчанию, если в запросе нет явной цели.

Парсер HEX (`parse_hex()` в `web.c`, `hex_to_bytes()` в `mqtt_client.c`) не
выделяет большой буфер на стеке: идёт по символам, пропускает любые разделители
(пробелы, запятые, `;`, `:`, `\r\n`), понимает префикс `0x`, сплошной
`41540D` и нечётную последнюю цифру как `0x0N`. Лимит — 512 байт на URL и MQTT.
Веб-интерфейс дополнительно вызывает `hexClean()` перед отправкой: пробелы
удаляются из HEX ещё до формирования URL/MQTT-примера и запроса `/api/send`,
поэтому наружу уходит `41540D`, а не `41%2054%200D`.

### 12.1 Адресная строка

```
http://<ip>/<пароль>?hex=41%2054%200D&target=3   → "OK bytes=3 target=3"
http://<ip>/<пароль>?hex=41540D                   → то же без разделителей
http://<ip>/<пароль>?log=50                       → последние 50 строк журнала
```

- `target` — `0` (USB), `1`, `2`, `3`; если не задан — `cmd_target`.
- Пустой/некорректный HEX → `400 ERROR: empty/invalid HEX`.
- При `cmd_mode == 1` (только MQTT) → `403 ERROR: URL channel disabled (MQTT mode)`.
- `?log=` читает журнал до 500 строк, по умолчанию 50.

### 12.2 MQTT

Клиент (`mqtt_client.c`) запускается только если `mqtt_uri` не пуст и
`cmd_mode` равен `1` или `2`. Keepalive 60 с, reconnect 2 с.

Адрес брокера можно задавать как `mqtt://host:1883`, так и просто `host` или
`host:1883`. `mqtt_normalize_uri()` приводит любой из этих видов к
`mqtt://host:port`; если порт не указан, подставляется `1883`. Поддерживается
IPv6 в квадратных скобках (`[::1]:1883`). Нормализованный адрес виден в
`mqtt.uri_effective`, в веб-подсказке и в логе подключения; в NVS остаётся то,
что ввёл пользователь.

| Направление | Топик | Payload |
|-------------|-------|---------|
| устройство ← команда | `<base>/rx`, `<base>/rx/1`, `<base>/rx/2`, `<base>/rx/3` | ASCII HEX: `41 54 0D` |
| устройство ← код | `<base>/code` | ASCII HEX; цель берётся из `<base>/target` |
| устройство ← цель | `<base>/target` | `0`, `1`, `2`, `3` или `usb`, `uart1`, `uart2`, `both`, `all` |
| устройство → результат | `<base>/result` | `OK bytes=3 target=2` / `ERROR: empty/invalid HEX` |
| устройство → код | `<base>/tx/code` | плотный HEX отправленной команды, например `41540D` |
| устройство → цель | `<base>/tx/target` | `0`, `1`, `2` или `3` |
| устройство → трафик | `<base>/traffic` | строка журнала (плотный HEX\|ASCII) |
| устройство → статус | `<base>/status` | `online` (retained) |

Подписка идёт на `<base>/rx/#` (по спецификации MQTT совпадает и с самим
`rx`, и с `rx/1|2|3`), `<base>/code` и `<base>/target`. Подписка только на
`rx` была убрана: вместе с `rx/#` она давала двойную доставку команды
и задвоение строк `[LOCAL > UART1/2]` в журнале.
Суффикс `/1|/2|/3` в конце `<base>/rx/...` перекрывает `cmd_target` только для этой
команды. Отдельные топики работают иначе: сначала публикация в `<base>/target`
задаёт цель (в RAM, до перезапуска или изменения настроек), затем `<base>/code`
отправляет только HEX-код на эту цель. Текущая цель видна в
`mqtt.target_effective` и в веб-подсказке. Каждая реальная отправка через
`uart_bridge_send()` дополнительно публикует код в `<base>/tx/code` и цель в
`<base>/tx/target` — отдельно от `<base>/result` и `<base>/traffic`. Оба `tx/*`
публикуются с `retain=true`, поэтому брокер хранит последние значения, и их видно
даже при подписке после отправки. Устройство на эти топики не подписано, поэтому
обратной связи нет. При подключении публикуется retained `online`;
при отключении сообщение остаётся в брокере (LWT не используется). Изменение настроек через
веб или `mqtt`/`cmdmode` вызывает `mqtt_apply_config()` — старый клиент
останавливается и создаётся новый.

Проверено на `broker.hivemq.com:1883`: статус `online`, команда в `<base>/rx/2`,
результат `OK bytes=3 target=2`, строка трафика в `<base>/traffic`.

## 13. Wi-Fi (`wifi.c`)

- Режим старта — **APSTA**.
- **AP:** SSID `UART_BRIDGE`, пароль `12345678`, WPA2-PSK, до 4 клиентов,
  канал 1, IP `192.168.4.1`.
- **STA:** SSID/пароль из конфигурации; `wifi_reconnect()` перезаписывает
  `wifi_sta_config_t` и вызывает `esp_wifi_connect()`. Энергосбережение
  отключено (`WIFI_PS_NONE`).
- Сканирование (`wifi_scan()`) блокирующее, до 16 точек; результат отдаётся в
  `/api/wifi/scan` и используется веб-карточкой.

### Автовыключение AP

1. На событие `IP_EVENT_STA_GOT_IP` сохраняется IP, публикуется
   `STA подключён, IP ...`, затем вызывается `esp_wifi_set_mode(WIFI_MODE_STA)`.
   Флаги `s_ap_enabled = false`, `s_ap_off_by_sta = true`; в журнал —
   `AP выключен (есть STA)`. STA-соединение при этом сохраняется.
2. На `WIFI_EVENT_STA_DISCONNECTED` вызывается `esp_wifi_set_mode(WIFI_MODE_APSTA)`
   (если AP был выключен именно из-за STA), флаги восстанавливаются, в журнал —
   `AP включён повторно (STA отключён)`, и запускается повторное подключение.
3. `/api/status` и веб-карточка показывают `wifi.ap_enabled`; при выключенном AP
   отображается «выключена (есть STA)».

Проверено на устройстве: после загрузки `connected:true`, `ap_enabled:false`,
STA IP `10.10.100.235`, SSID `Dacha-2.4`.

## 14. Время (`time_sync.c`)

- SNTP в режиме `ESP_SNTP_OPMODE_POLL`, `SNTP_SYNC_MODE_IMMED`, один сервер
  (`CONFIG_LWIP_SNTP_MAX_SERVERS=1`), опрос раз в час
  (`CONFIG_LWIP_SNTP_UPDATE_DELAY=3600000`). Настройки задаются в вебе или
  командами `ntp <server> [tz]`.
- Часовой пояс — POSIX TZ через `setenv("TZ", ...) + tzset()`; по умолчанию
  `MSK-3`. Примеры: `UTC0`, `CET-1CEST,M3.5.0,M10.5.0/3`.
- Собственный флаг `s_synced` выставляется в колбэке `sync_cb()`, потому что
  IDF сбрасывает `sntp_get_sync_status()` сразу после колбэка. Благодаря ему
  `time_sync_synced()` остаётся `true`.
- `time_sync_format()` отдаёт `dd.mm.yyyy HH:MM:SS` или
  `--.--.---- --:--:--` до синхронизации. `time_sync_offset_min()` читает
  смещение через `strftime("%z")` (для `MSK-3` — `180`).
- После синхронизации метки журнала и часы в мониторе показывают реальное
  время; до неё — uptime. Время синхронизации на практике 30–45 с после boot.
- Важно: подключается только `esp_sntp.h`; совместное включение
  `esp_sntp.h` и `lwip/apps/sntp.h` даёт конфликт объявлений.
- `time_sync_apply()` (`esp_sntp_stop()` + сброс статуса + `start()`) вызывается
  при изменении сервера/TZ из веба или CLI.

## 15. OTA (`ota.c`)

- Таблица разделов `partitions_ota.csv` — два слота приложения.
- `ota_init()` при старте проверяет состояние текущего слота; если
  `ESP_OTA_IMG_PENDING_VERIFY`, вызывает `esp_ota_mark_app_valid_cancel_rollback()`
  (прошивка подтверждена, откат отменён).
- `ota_start(url)` копирует URL и создаёт задачу `ota` (стек 8192):
  `esp_https_ota()` с `esp_http_client` (timeout 15 с, keep-alive) и набором
  корневых сертификатов `esp_crt_bundle_attach` для HTTPS.
- Успех → запись «успешно, перезагрузка», событие `EV_OTA`, задержка 1,2 с,
  `esp_restart()`. Ошибка → строка `ошибка: <esp_err_to_name>`, событие в журнал.
- Пока идёт обновление, `ota_busy() == true`; повторный `ota_start` игнорируется.
- Запуск: веб-карточка OTA, `POST /api/ota` или команда `ota <url>`. Статус —
  в `/api/status` (`ota_busy`, `ota_last`) и в шапке веба.

## 16. Потоки данных (сводка)

### 16.1 Трафик UART

```
UART1 RX → uart1_rx → forward(EV_FROM1) ─┬─→ UART2 TX (если bridge)
                                        ├─→ event_bus → журнал
                                        │              ├─→ WebSocket → браузер
                                        │              ├─→ MQTT /traffic
                                        │              └─→ Telnet (monitor on)
                                        └─→ USB mirror (если mirror)
UART2 RX → uart2_rx → forward(EV_FROM2) → ... симметрично
```

### 16.2 Команда из веба / URL / MQTT

```
Web /api/send ─┐
URL ?hex=      ├─→ parse_hex → uart_bridge_send(target) → UART1/UART2/оба
MQTT /rx[/n] ─┘                                      └→ EV_TO1/EV_TO2 → журнал/WS/traffic
                                                       └→ "OK bytes=N target=T" → /result
```

### 16.3 Команда из USB/telnet

```
USB RX → cli_usb_bytes → cli_process ─┐
Telnet RX → handle_byte → cli_process ─┴─→ send/sendhex/raw → uart_bridge_send(s->target)
                                        └─→ target/raw/baud1/... → config + действия
```

## 17. Сборка и прошивка

Проверено на ESP-IDF **v5.5.2** (совместимость v4.4+/v5.x), цель `esp32`.

```powershell
. C:\Espressif\frameworks\esp-idf-v5.5.2\export.ps1
idf.py set-target esp32
idf.py build
idf.py -p COM4 flash monitor
```

Результат сборки: `build/PassThroughUART.bin` (≈1,1 МБ, свободно ~19% раздела).

Ключевые опции из `sdkconfig.defaults`:

```
CONFIG_PARTITION_TABLE_CUSTOM=y
CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_ota.csv"
CONFIG_HTTPD_WS_SUPPORT=y
CONFIG_LWIP_MAX_SOCKETS=16
CONFIG_LWIP_SNTP_MAX_SERVERS=1
CONFIG_LWIP_SNTP_UPDATE_DELAY=3600000
CONFIG_ESP_CONSOLE_NONE=y
CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=y
CONFIG_FREERTOS_HZ=1000
CONFIG_ESP_MAIN_TASK_STACK_SIZE=4096
```

`CONFIG_LWIP_MAX_SOCKETS=16`, `cfg.max_open_sockets=13` и `WS_MAX_CLIENTS=8`
подобраны так, чтобы HTTP + WebSocket + Telnet + OTA не исчерпывали сокеты
(раньше это приводило к «залипанию» веб-переключателей).

## 18. Ограничения и особенности

- Журнал живёт только в RAM и теряется при перезагрузке. Для постоянного лога
  нужно дописывать строки в `event_bus_publish()` в FatFS/SPIFFS.
- Токен cookie детерминирован (производный от хеша пароля). Это упрощает
  работу без хранилища сессий, но не обеспечивает «выход из всех сессий»;
  смена пароля меняет токен.
- MQTT-пароль хранится в NVS открытым текстом (как и пароль Wi-Fi) —
  физический доступ к флешу считается trusted.
- AP отключается только если STA получил IP. Если роутер пропадёт — AP
  включается снова, и устройство остаётся доступным по `192.168.4.1`.
- На ESP32-WROVER не используйте GPIO16/17 для UART2 (там может быть PSRAM);
  по умолчанию выбраны GPIO25/26.
- Telnet: максимум 4 клиента; WebSocket: максимум 8.
- `sntp_get_sync_status()` сам сбрасывается после колбэка — используйте
  `time_sync_synced()`, а не прямой вызов IDF.
